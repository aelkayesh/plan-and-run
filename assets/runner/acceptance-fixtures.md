# Local acceptance fixture contract

Workers write source/tests and a mapping; they never select host argv, environments, remote services, ports, installations or commands. The frozen profile supplies every criterion/gate obligation. NN-acceptance-mapping.json enumerates each required case exactly, with every criterion/gate pair referencing substantive assertion IDs. Fresh read-only review checks their purpose against original acceptance before execution and again against captured evidence.

## Hand off to parent acceptance

When the implementation and complete mapping are ready but configured parent gates remain, return the ordinary worker result fields with `status: "acceptance-ready"` and an empty `blockers` array. Keep the required validation/handoff paths in the result; neither final file is required for this handoff. Preserve existing partial artifacts and never write a successful receipt for deferred gates. This status is valid only for the current nonmanual package's existing strict profile. A sandbox restriction on a configured parent gate is a deferred parent check; a missing service, prerequisite, permission or product decision is still a genuine blocker.

A supervisor may explicitly return `action: "acceptance-check"`, `classification: "environment"`, `recipe_id: null` and no blockers after inspecting a truthful blocked attempt. It cannot convert arbitrary blocked prose into a request, change the profile or supply commands, recipes, environments or overrides. Legacy/no-profile and manual packages cannot use either handoff.

The parent saves the request identity and original worker/finalizer conversation before mapping review, executes only the frozen fixed gates, and reviews actual evidence. Interruption resumes that parent phase and reuses only current, hash-verified evidence with verified cleanup. Failed gates return to bounded repair; source drift, provider/protocol failures and repeated handoffs retain the existing cumulative budgets. Repeating `acceptance-ready` after current evidence without making progress cannot create unlimited finalization attempts.

Once parent acceptance passes, the saved original worker/finalizer resumes with exact evidence pointers. Read and attribute those parent checks, run any remaining checks, and write truthful completion artifacts for the new current attempt. Parent gate success alone does not complete a package. Source edits can require fresh acceptance. The parent still validates the final completed result, receipt and handoff and verifies current acceptance before advancing.

## npm and production build

npm-checks requires existing vitest run and tsc --noEmit scripts. It collects then executes the full default suite and typecheck in an owned source copy. Map all full test names in the selected required files plus reserved npm-test and npm-check. Every required file/case must pass with zero skips; unrelated opt-in SQL skips in the default run cannot establish SQL acceptance. Names must be unique across required files. Collection and execution identities must agree.

production-build requires the existing next build script and preinstalled dependencies. Its only case ID is production-build, with no mapped files. Build output comes from a fresh owned copy. Parent retains and hashes BUILD_ID, build-manifest.json, routes-manifest.json and prerender-manifest.json alongside logs. No install/download, config rewriting, changed npm scripts or source-checkout build reuse is authorized. Missing prerequisites and failing builds remain unresolved.

For projects declaring `requirements.txt` or `requirements-protocol.txt`, preflight also binds the existing Python interpreter (`TRIALPROOF_PYTHON` or `.venv/bin/python`), installed requirement versions and dependency identity. The fixed offline probe checks PDF extraction and cached `o200k_base` tokenization when those packages are declared. Missing packages, incompatible pins or missing tokenizer data block before a worker starts; no install or download occurs. Isolated checks receive the bound absolute interpreter, disabled user-site/bytecode writes and an owned copy of tokenizer data. Repository Python source still comes from the isolated source copy. Python-related environment injection is scrubbed, and paid benchmark execution is explicitly disabled. The interpreter may have a different supported architecture from Node; both identities are recorded.

Mappings use the JSON result's canonical `fullName`. The adapter compares Vitest collection display names using the result's structured ancestor titles and test title; a literal ` > ` inside a title is preserved. Missing, duplicate, ambiguous or skipped required cases still fail.

## New PostgreSQL suites

Use tests/acceptance/NN/NAME.postgres.test.ts (one filename level). The parent owns a fresh marked local container from its fixed preinstalled image. Selected test processes receive CODEX_PLAN_TEST_DATABASE_URL, CODEX_PLAN_FIXTURE_ID (fresh UUID), CODEX_PLAN_PACKAGE_ID and CODEX_PLAN_PLAN_HASH.

A suite may skip when the explicit URL is absent in the unrelated default run. Once selected it must run every case, including negative/rollback behavior. Before any mutation, query public.codex_plan_fixture and require exactly one row whose fixture_id, package_id and plan_hash match those environment values, synthetic=true, and purpose=package-NN. Never skip on marker mismatch, create/adopt/rewrite a marker or connect to a fallback database. Close test clients in teardown. Parent deletes only its exact owned container. Tests/report JSON expose every full case name; omitted or skipped required assertions fail. Legacy presets are exact reviewed file/flag/database conventions; workers cannot invent presets or widen files.

The reviewed legacy preset set includes `sites-legacy`, `study-management`, `access-storage`, `access-policy`, `access-adapters`, `sites-lifecycle`, `operations` and `benchmark-store`. Each pins one complete existing suite. `operations` requires its existing `section4_test` database on loopback port55444. `benchmark-store` pins the complete `tests/benchmark-store.test.ts`, uses a random fixture database/loopback port and explicit synthetic PostgreSQL credentials, and applies the fixed repository `deploy/managed/benchmark-migration.sql` after verifying the universal marker. Its required grant role is created as `NOLOGIN` inside that new container; setup bytes and verified schema/trigger state are recorded. Missing or symlinked setup files fail before container creation. The full benchmark suite includes two explicitly SQLite cases (legacy reservations and backup/restore); they remain required and must not be reported as PostgreSQL coverage.

Legacy markers preserve their existing purpose values while the universal marker and evidence identify the currently executing package. Fresh regression checks never alter accepted predecessor receipts or scheduling state. Site packages13/14 require all eight existing suites alongside their universal SQL suites; package08 additionally requires operations and package10 benchmark storage. Every required suite must be mapped and pass in full, with zero required skips.

## Package browser cases

Use one tests/acceptance/NN/NAME.browser.mjs file. Export cases, an array of unique {id, async run({page,baseURL,assert})} entries matching the mapping. Parent supplies an installed Chromium browser, fresh build and fixed loopback server. Each case gets a new context; non-loopback requests and service workers are blocked. Use provided assert.equal, assert.deepEqual, assert.ok or awaited assert.rejects for substantive UI assertions. A case with no harness assertion fails. Do not launch servers/browsers, choose URLs/ports, import secrets or send invitations/AI requests. Include package-specific authorized/denied behavior; an unrelated smoke test cannot satisfy the current package's UI criteria.

Parent captures a full-page PNG per case, complete assertion report, source/build identity and process logs. It checks complete unique case/screenshot coverage, positive assertion counts and hashes. Browser/server/helper processes remain in their owned process group; unknown identities prevent deletion/retry. Screenshots and model review are engineering evidence, not proof of arbitrary correctness.

## Durable evidence and retries

Passed gates resume only with current execution-input identity. One changed source/context/mapping generation charges one refresh even when multiple gates become stale; default cumulative limit two. Verified-clean host timeouts have a separate cumulative two-retry budget. Failed/obsolete evidence and timeout journal snapshots remain immutable. Exhaustion requires an explicit larger --max-evidence-refreshes; increasing a budget retains counters/history and a current successful worker. Unknown cleanup must be reconciled before retry.

Malformed worker/supervisor/planner/subtask/reviewer outputs receive exact same-session correction feedback within a separate default two-retry protocol budget. Rejected bytes or missing-output observations are retained/hashed; rejected actions never execute. External blockers stay blocked. Legacy manifests retain receipt verification and historical accepted entries retain their original obligations.
