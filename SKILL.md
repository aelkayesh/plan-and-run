# Plan and Run

Turn the requested work into a durable multistep plan and a CLI that executes its authorized steps sequentially, stopping at completion or an actionable blocker. Keep packages proportional to the task; do not pad a small fix into a large project.

## Select the mode

- **Plan / do not implement:** inspect the repository, save the plan and runnable bundle, validate it, and provide the command. Do not start implementation workers.
- **Implement / build / fix:** prepare or reuse the reviewed plan and execute within the scope already authorized. Do not stop at proposing a plan or ask again for permission already given.
- **Implement step N / resume:** read existing state and handoffs; select exactly the requested range. Do not restart completed packages or expand to the entire roadmap.
- **Create a runner for me to launch:** prepare and test the bundle; leave execution to the user.
- **Runner worker:** if `CODEX_PLAN_WORKER=1`, the prompt supplies `PACKAGE_ID`/`ATTEMPT_ID`, or an orchestrator assigns a bounded task with a completion contract, perform that task directly. Do not scaffold a new plan or start a nested runner.

## Prepare

1. Confirm the actual checkout, repository instructions and existing changes. Find any authoritative plan before creating another. Preserve unrelated edits, data and active services.
2. Save independently executable packages with prerequisites, bounded deliverables, actual checks, acceptance gates, scope limits and handoffs. Use the smallest useful number of packages and include integrated acceptance when needed. Break large work at testable boundaries.
   For acceptance-driven autonomy, author an explicit strict profile with original criterion IDs/types/purposes and required typed gates. Workers propose mappings; fixed parent adapters and fresh read-only semantic review decide acceptance. Read [adapter scope](references/compatibility.md#optional-strict-acceptance) and the generated runtime `acceptance-fixtures.md` before selecting those capabilities. Omission retains legacy receipt verification.
3. State task-specific constraints and already-granted authority in a shared contract. Use `manual: true` only for a genuinely unresolved decision or external authorization, not a fixed package number. Such a boundary must not prevent earlier authorized work.
4. Select recovery in the authored spec: ordinary sandbox source repair is enabled by default; authorize fixed `npm-checks` only where the user has authorized those local checks. Omitted recipes never permit host execution. Read [plan-format.md](references/plan-format.md), author the complete specification JSON, and call the bundled `scripts/prepare.mjs`. It installs a self-contained runner into the project and refuses to overwrite existing plans or progress.
5. Plan prerequisites for the entire selected executable range before any worker starts: installed Node/npm/dependencies, any declared Python runtime/packages and local tokenizer data, the selected Codex executable/profile and local authentication, every required fixed host capability, and dependencies before the range. For strict profiles, assign every criterion to all required capabilities now; an omitted recipe cannot be invented after execution starts. Future mapping/test files are worker deliverables, while missing installed tools or local services are prerequisites. Use [the complete strict example](references/strict-acceptance-example.json) and the preflight planning table in [plan-format.md](references/plan-format.md).
6. Review generated instructions against the request. Resolve incomplete requirements before setting the manifest to `ready: true`. Run `dry-run` for sequence/boundaries and `preflight --from NN --to NN` for the exact intended range. Preflight uses local readiness checks without inference and reports missing prerequisites before a worker. Never mark an unfinished draft ready simply to start execution.
   The fixed Azure CLI user-auth probe reads existing helper/profile/plaintext-cache identities and matching credential presence without running an auth command or refreshing credentials. Presence does not establish token validity or remote authorization. Unsupported mechanisms and unresolved repository provider/profile precedence remain explicit blockers; preserve the selected configuration. See [runner-contract.md](references/runner-contract.md#preflight-background-ownership-and-results).

The bundle lives at `docs/implementation-plans/<slug>/`: request, shared contract, package plans, manifest, worker contract, index and `run.mjs`. The prepare script prints exact commands. Read [runner-contract.md](references/runner-contract.md) for receipt schemas, retry controls and recovery.

## Execute and monitor

- Start the generated runner for an implementation request. Use foreground `start`/`resume` unless unattended/background execution is requested; omitting the subcommand also selects foreground `start`. Explicit `launch` runs preflight and detaches with a durable session after acquiring the same plan lock. Do not silently detach. While executing in this session, monitor progress and handle fixable local blockers. Launch readiness and process liveness are not acceptance or completion.
- For requested unattended execution, provide `launch`, `status --json`, `logs` and `stop` commands with the exact range. Keep the reported session ID and result path. `stop --session UUID` challenges the live owner and waits for cooperative worker/helper cleanup; it never kills an unrelated PID. Resume with the same selected range and options; accepted work, cooldowns and budgets remain saved.
- On macOS, launch confirms an owned idle-sleep assertion tied to its runner and verifies cleanup on exit. Unexpected assertion loss aborts work; unresolved ownership or cleanup prevents a successful result. No persistent service or reboot restart is installed. Poweroff, reboot, closed-lid sleep, missing authentication/services and exhausted finite budgets remain explicit limitations. Local authentication readiness does not prove future remote authorization.
- In worker/finalizer mode, return `acceptance-ready` with no blockers when implementation and the complete mapping are ready for configured strict parent gates. No successful final receipt is needed or permitted for deferred gates. Parent acceptance persists the request, checks the frozen profile and resumes the original actor with exact evidence to write truthful current completion artifacts. Genuine missing services/permissions/decisions stay blocked; a supervisor can explicitly request `acceptance-check` only for the existing strict profile with environment classification, no recipe and no blockers. Legacy/manual/no-profile packages cannot use this handoff. Repeated ready results retain finite no-progress/finalization budgets.
- Let the runner own sequencing. Each package gets a fresh conversation; ordinary retries resume its saved conversation. Completion requires its actual acceptance checks and matching result, validation receipt and handoff. Never write fake completed state or skip failing gates.
- Normal start/resume automatically diagnoses eligible failures with a bounded recovery supervisor, preserves partial work, resumes the saved worker, and runs only frozen, explicitly authorized host recipes. Rate limits retain provider-aware cooldowns. Transport reconnects use a 10-second base plus jitter and a 30-second local cap, with provider minima and existing saved deadlines preserved; repair, transport, evidence refresh and no-progress budgets persist across restarts. Authentication/billing/configuration errors, unknown authority, unavailable services, tampering and exhausted budgets produce actionable needs-attention output. Never install dependencies or edit credentials/npm scripts through recovery.
- Explicit TPM pressure can trigger one bounded subdivision after cooldown: by default, two failed attempts, or one request explicitly exceeding the per-minute token ceiling. A fresh read-only planner proposes 2–6 sequential subtasks; each starts a fresh context, inspects partial effects and records a compact source-bound checkpoint. A fresh finalizer must run the original package acceptance and write its completion records. Checkpoints never complete the parent, and subtasks cannot recursively split or expand its scope.
- The default rate retry budget is eight; fresh retry rotations within the subdivision default to three. Counts, cooldowns, accepted checkpoints and pending work survive restart. `--max-rate-retries 0` explicitly selects unlimited rate retries; exhausted finite budgets require inspection and an explicit increase. Ordinary RPM throttling, ambiguous rate errors and context-window limits do not trigger subdivision. Context capacity does not increase TPM quota. Automatic provider/model switching is not implemented; any future switch is a separate user decision.
- Keep workers within the requested scope and authority. A local implementation request does not authorize deployment, original-data migration, external messaging or additional paid product inference. Honor prior explicit authorization. When approval is actually needed, first prepare the concrete reviewable action and save the boundary/handoff.
- Use the same command after interruption. For a bounded request, use `--step NN` or `--from NN --to NN`. Do not regenerate a plan to discard state.
- Treat a manual boundary or blocked package as unfinished work. All requested authorized packages and acceptance gates must pass before claiming the task complete.

## Delivery and maintenance

Give the saved plan location, exact preflight/start/resume commands or requested launch/status/logs/stop commands, durable session/result locations, verification results and current execution state. Distinguish prepared automation, fake-worker tests and completed feature work. Keep the final reply concise.

After changing scripts, test the generator and runner with fake Codex workers. Do not use real inference merely to test orchestration. Generated bundles are pinned copies; never silently upgrade them. A requested runtime replacement uses read-only mismatch diagnostics and an explicit hash-bound `runtime-prepare`/`runtime-apply` audit, preserving package state and evidence. Host checks use isolated test directories and scrub child credentials; environment scrubbing is not a security sandbox. Run `npm run check` in the skill repository; when skill-creator is installed, also use its metadata validator.
